# Chat — Agent Guide

Chat is the minimal chat-first agent-native app. `/` redirects to shared sign-in, then `/home`, the editable Get started page. Chat lives at `/chat`; new chats start there. Actions carry capabilities; screens exist only for durable workflows.

## Core rules

- UI feedback: target 100 ms, never exceed 400 ms; acknowledge before network work.
- Normal app data must flow through actions. Keep actions deterministic and focused; use agent chat/AgentSidebar for AI work and follow-ups in the same thread. Keep structured state in SQL and large files in configured storage; persist references only.
- For external integrations, inspect the workspace/provider connection catalog first; reuse its scoped resolver. Never hardcode credentials, webhook URLs, or private/customer data.
- Never fabricate. Report failures and recover; verify writes by reading the row or screen. Navigation is in `<current-screen>`; use `view-screen` for fresh visible-record details.

For custom branding, keep `server/plugins/agent-native-email-branding.ts` aligned: `app.name` appears in transactional email and optional `app.logoUrl` must be an absolute HTTPS URL.

## Application state

- `navigation` describes the view and selected ids. Chat is `chat` at `/chat` and `/chat/<threadId>`; the Get started page is `home` at `/home`; `/` opens shared sign-in/signup.
- Use `navigate` when supported and `view-screen` for a fresh read of visible details; basic navigation is already in `<current-screen>`.

## Building a domain app

Choose the primary workflow and route before editing. Add a domain route under `app/routes/` and set `app.homePath` in `server/plugins/agent-native-email-branding.ts` with `defineAppConfig`. The default Get started page lives at `/home`, and Chat stays at `/chat`; edit `app/routes/home.tsx` when replacing that page with a domain-specific home. Add a static link in `app/components/layout/Sidebar.tsx` before `ChatThreadsSection`; `Header.tsx` uses `APP_TITLE` elsewhere. Shared sidebar and AgentInspector remain.

Use `adding-a-feature` for functional parity and `frontend-design` for a user-facing screen. Keep feature guidance here; do not rewrite `README.md` or `DESIGN.md`. After all edits, run one typecheck, one doctor check, and one browser smoke of the primary workflow, including overlap rejection, cancellation freeing the slot, and authenticated landing. Skip production build and extra test suites.

Before building common workspace or agent UI, read `agent-native-toolkit`; for supported customization, read `customizing-agent-native`.

- Guarded verification: run `pnpm agent-native:doctor`; fix findings before done.

## Local model runtime

In development, the home/chat transports use the app’s loopback-only Codex CLI bridge (`app/lib/agent-transport.ts`), backed by Agent-Native’s native Code runner. Use `gpt-6.1-sol` with low reasoning (light thinking), enforced by the app-owned CLI shim in `scripts/local-codex-bin/codex` because Core 0.223 does not forward that setting. Start with `pnpm dev:local` to select the desktop executable and scoped PATH shim. Reuse the host’s Codex login; do not copy tokens or call Jev/OpenAI API-key providers as a fallback. Local endpoints require browser-cookie authentication and same-origin loopback requests, allow one active turn per caller, and run Codex in read-only mode. Native Code history is stored under ignored `data/local-codex`; client chat uses the existing AgentKit shell. Production retains the standard Agent-Native transport and the planned Jev/OpenAI configuration. Domain actions use the bounded protocol described below; live source reads use the app connections described in Live source import.

## Feature review workspace

The primary route is `/features`, with `/features/<id>` for a review. `/home` redirects there. The shell stays mounted. Features use framework ownable columns/shares, private by default, with public sharing disabled. Sample excerpts are synthetic; live imports are explicitly labelled captured provider text. Owner roles remain manually assigned, not connected company identities. Use the existing Share control for real workspace access. Only the resource owner may approve; editors may record replies and proposals.

Read `.agents/skills/feature-coordination/SKILL.md` for workflow semantics. SQL schema/migrations belong in `server/db` and `server/plugins/db.ts`; lifecycle transitions in `server/features/lifecycle.ts`; resource access/revision checks in `server/features/store.ts`; wire constants and validation in `shared/features/types.ts`; domain UI in `app/features/coordinator`.

**Question collection.** `data.questions` holds only additional suggested questions (max 20, ids unique, `primary` reserved). The primary question is always projected by `getFeatureQuestions` (`shared/features/questions.ts`) from the legacy `question`, `discord` and row status, which stay authoritative for it and for all Discord delivery history; existing actions keep writing those fields. `askApproval` (permission to ask) is separate from decision approval (`approvedBy`/`approvedAt`). A legacy primary whose delivery left `draft` projects as approved with provenance `legacy_send_confirmation` and no actor/time; no explicit approval was ever stored. Dismissal is editor-reversible via `restore` and revokes an existing approval. Ask review is owner-only and frontend-only: approval needs a selected recipient and a pending, undismissed question; rejection can follow pending or approved; reopening a rejected question returns it to pending (never straight to approved). Editing text, suggested responsibility or recipient of an approved question invalidates the approval; evidence edits do not. Rejected questions cannot be edited until reopened. A question whose delivery left `draft` is frozen: its history is preserved and it cannot be edited, dismissed, reviewed or reopened for another send. Recipient selection is one of: a responsibility with a saved role mapping (role snapshot); or, owner only, an existing server role (`recipient: {discordRoleId}`) or a verified individual (`recipient: {discordUserId}`, stored as `recipient.person`, mutually exclusive with `role`). `get-feature-discord-directory` (owner, GETs only) lists people with their non-managed role associations and whether they can view the linked channel (effective permissions from role and channel overwrites; the guild owner counts as visible), and reports coverage explicitly: the member list needs the bot's Server Members Intent (otherwise `unavailable`, with selection by Discord user ID still verified against a single-member read), at most 2000 members are read (`partial`), and people whose visibility cannot be computed are `unknown` and not selectable. Only visible, non-bot members can be selected; a failed verification never substitutes another recipient. Discord membership and roles never establish responsibility or approval authority; `owner` stays an explicit, separate assignment. An individual draft snapshots the person, mentions `<@id>` with `allowed_mentions` limited to `users:[id]`, and send re-verifies membership, channel visibility and the bot's view/send permission before reservation. Each approved suggestion is delivered independently through its own `data.questions[].discord` thread: the owner saves a draft (`update-feature-discord` `question_draft`) that snapshots the exact text, the recipient role and the channel, reviews it, then sends with `send-feature-discord-question` + `questionId`. A send requires ask approval, an unchanged snapshot (text, recipient role, channel) and the same effective-permission checks as the primary; it reuses the feature's saved channel and never retargets when role mappings change. Revoking approval (edit of text/owner/recipient, dismiss, reject) discards an unsent draft. After reservation the outcome is written against the latest revision so other questions' deliveries cannot block or overwrite it; uncertain deliveries are reconciled per question by nonce-bearing content (`check-feature-discord-replies` + `questionId`), never reposted. The channel cannot be replaced once any suggestion left draft. Recording a suggestion's reply as a decision is not implemented. The feature page's `QuestionList` (`app/features/coordinator/QuestionList.tsx`) lists the primary question (read-only; its replies, proposal and Discord delivery stay in the sections below) and every suggestion with origin, evidence, responsibility, recipient, ask approval and delivery. It edits, dismisses/restores and chooses recipients through `update-feature-suggested-question` (responsibility recipients need a saved role mapping; the owner may instead choose a verified person or role from the directory; unresolved ones stay visibly unresolved), and the owner approves/rejects/reopens through `review-feature-suggested-question-ask`. Agent chat shows a compact card through `QuestionChatCard` (registered in `app/root.tsx`, resolved by the `ChatWidget` slot in `ChatRouteContent.tsx` and the sidebar registry, populated by the local Codex route's widget event) listing pending **proposals** (`data.proposals`), which are separate from pool questions: the agent saves them with `propose-feature-questions`, Approve adds a new pool question through `review-feature-question-proposal` (warning first when a similar pool question exists, with "Add anyway"), and Reject only hides the proposal and never changes the pool. The chat card and page share `useQuestionActions` and re-read `get-feature`; only the chat card renders pending proposals. Approval comes only from the signed-in user's frontend click, never from agent output.

A user-requested agent review reads the captured sources via `get-feature`, saves findings with one `propose-feature-questions` call (the protocol validates the arguments with the shared schemas before dispatch) and shows them with `show-feature-questions`; the owner can review them in chat or on the feature page. `create-feature-suggested-questions` writes straight into the pool and is not in the local agent allowlist. Repeated reviews only add new findings and never overwrite approved or sent work. The end-to-end first-phase path is in `docs/discord-review.md`.

Pending question proposals live only in the agent chat card until the owner accepts or rejects them. The feature page shows the question pool only, so an accepted proposal appears on the page after approval; accepting adds a question but does not approve asking or send it. The chat card uses the owner-only proposal actions and duplicate warning.

Local Codex's bounded JSON action protocol is in `server/features/local-agent.ts`. It uses the same validated actions with request-scoped identity; it never receives authentication tokens. Its allowlist excludes approval and all outbound integrations. The sidebar and full-page chat use the same supported local runtime. User-facing UI copy belongs in the English catalog's `coordinator` namespace, with framework fallback for other locales. Do not promote synthetic snapshots to live source state.

## Live source import

The feature list has a live import form. It reuses the caller's authenticated Atlassian MCP connection through public `mcp-client` APIs, with provider URL matching, and the scoped Figma provider API runtime. It performs GET/read tools only. Each import creates a new private SQL aggregate; reimport never overwrites a sample or approved review. `data.sample` distinguishes provenance. Source URLs, provider versions, capture times and coverage notes accompany bounded text. Capture is not continuous monitoring. The local agent reads these records through `get-feature`; it does not directly invoke provider tools or receive credentials.

A failed selected source prevents creation. Choosing no design produces a two-source review with a prominent design-unverified notice, never a synthetic replacement. Confluence's statements about a design are reported claims until independently read from Figma. Text layers do not establish actual visibility, geometry or prototype behaviour. Comments, attachments, macros and Jira custom-field acceptance criteria are outside this initial capture scope. Never claim those were reviewed. Source readers and URL validation belong in `server/features/live-sources.ts` and `source-input.ts`; provider-specific response fixtures in adjacent tests.

The UI now explicitly chooses Google Stitch, Figma or no design; Stitch is the current UI default. `includeFigma` defaults apply only for legacy callers without `designProvider`. The Stitch reader in `server/features/stitch.ts` pins the actual Google MCP endpoint, scopes reads to the authenticated principal, allowlists read tools and uses inert, bounded HTML extraction. Only the existing scoped API-key header may be reused for Google-origin asset downloads; never expose it or send it to a CDN/redirect. The saved source identifies the selected screen and text coverage.

A Stitch import also captures the selected screen's screenshot. `server/features/screenshots.ts` validates the bytes (PNG/JPEG/WebP, ≤1 MB), stores them in configured private blob storage under `features/<featureId>/…`, and persists only the opaque handle plus capture time and coverage notes on that source. `get-feature` attaches the stored image to agent tool results as `_agentImages` after its access check; UI reads stay text-only, and the browser fetches the image through the authenticated `/api/features/<id>/screenshot` route. The local Codex CLI transport writes a text prompt to stdin and cannot display images, so the local agent receives an explicit `screenshotNotice` instead of a claim of visual access; the production Agent-Native transport receives the image. A screenshot proves only the captured image at import time, not interactions, responsive behaviour or later changes. See `docs/stitch-live-review.md` in the project root for use and validation.


## Discord review

Live reviews may connect a standard server text channel. Use the registered user-scoped `Discord bot token` secret, never an environment fallback. The server API adapter pins Discord's HTTPS origin, validates IDs and paths, disables redirects, and bounds responses. Only the feature owner through the frontend may post a saved draft after reviewing the exact text and destination. Agents cannot post. Reservation with revision compare-and-set precedes POST; uncertain delivery must be reconciled, never blindly retried. Verify success with a GET of the posted message and persist the message ID. Replies are captured only on explicit latest-100 checks, then separately selected and freshly revalidated before recording with source provenance. A reply is not approval. This is not a Gateway listener or DM integration. See `docs/discord-review.md` in the project root for setup, coverage and live-test instructions.


### Discord follow-ups

One optional follow-up per sent question. The owner opts in in the send dialog, chooses 1–3 hours, and reviews the exact follow-up text, recipient and channel before sending. The schedule is written only after the original POST is confirmed by readback; opting in or cancelling never sends. `data.<thread>.followUp` in the question's Discord thread is the durable record (JSONB, additive field; old rows parse without it). The scheduled Netlify function `feature-coordinator-discord-followups` (emitted by `scripts/emit-followup-scheduled-function.mjs` from `postbuild`) calls `POST /api/discord-followups/run` every minute with `DISCORD_FOLLOWUPS_SECRET`; the route processes at most five due follow-ups in an eight-second budget and returns counts. Local `pnpm dev` has no durable scheduler and must not be described as one. See `docs/discord-followups.md`.

A qualifying reply is an explicit Discord reply to the original message, in the same channel, non-bot, non-empty: from the snapshotted individual, or from a member who currently holds the snapshotted role (membership is fetched fresh). Role membership is not authority, and other replies do not stop the follow-up. The worker pages back up to 500 messages; if it cannot reach the original or verify membership, it stores `unverified` and sends nothing. Before POST it rechecks the channel, bot identity, current notification permission, original message, question text, recipient, ask approval, status and cancellation. A reply can still arrive between that check and Discord's acceptance; the follow-up is not deleted in that window. A qualifying reply stops the follow-up but never records an answer, proposes a decision or approves anything.

The worker claims with a feature-revision compare-and-set (`scheduled` → `sending`, two-minute lease, attempt count) before any network call, so concurrent workers cannot both POST. A crashed or expired claim is reconciled by finding exactly one matching bot message (content + `message_reference`) and marking it `sent` or `uncertain`; it is never reposted. `failed` means Discord refused before creating a message (400/401/403/404/429); `uncertain` means a timeout/5xx/readback mismatch may have been accepted. `sent` and `uncertain` are terminal; `failed` and `cancelled` can be rescheduled. A sent question is already frozen, and the worker's snapshot check is a second guard against future edit paths.

### Discord people and roles

The People and roles section maps Product owner, Frontend developer, Backend developer and Designer to real Discord roles per feature. The canonical responsibility constants live in `shared/features/participants.ts`, re-exported by `shared/features/types.ts`. Mapping schemas remain optional for existing reviews. Role discovery and mapping writes require feature ownership and use the current caller’s scoped bot credential. Exclude everyone and managed roles, validate IDs against the connected guild before saving, and preserve revision checks. Saving a mapping does not grant app access or change sent messages/existing drafts. New drafts snapshot the mapped role of the current question owner; exact recipient and text are shown before posting. Allow only that snapshotted role in Discord `allowed_mentions`; broad/user/reply-author notifications stay disabled. Saving a draft preserves its explicit recipient without notification checks. Recheck role existence and effective bot channel permissions before POST; distinguish missing, denied, and unverified. Reload roles shows current channel-specific notification eligibility. Use a disabled `useActionQuery` plus explicit refetch for the Load server roles read. No role membership is inferred as business approval, and no Gateway listener is included.
