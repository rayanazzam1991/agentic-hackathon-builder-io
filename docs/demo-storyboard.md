# Feature Coordinator: planned three-minute demo

All public data is invented and labeled. Record actual working behavior; never present fixture replies or prepared model outputs as live integration results.

| Time | Action | Outcome |
| --- | --- | --- |
| 0:00–0:25 | Open one feature with Confluence specification, Jira stories, Figma frames, and named owners | Show the team’s scattered working context |
| 0:25–0:55 | Refresh and inspect an explicit open question plus a possible permissions mismatch | Evidence-backed blocker with exact sources |
| 0:55–1:25 | Review the question and send it to the configured Discord feature thread | Agent takes a concrete coordination action; delivery is visible |
| 1:25–1:55 | Receive the PO’s actual reply and inspect its linked decision proposal | Answer is correlated and attributed, not silently approved |
| 1:55–2:25 | Responsible person approves; inspect and publish the targeted Confluence update | A traceable agreed rule with a version check |
| 2:25–3:00 | Show targeted notification, resolved question, and decision timeline; refresh again | Team is informed and the agent avoids duplicate work |

Example: the specification allows project members to archive, while the design shows Archive for managers only. The question asks the PO which rule applies. The approved response is managers only. The update and notification state exactly what changed and which roles are affected. Neither design nor specification proves implemented server authorization.

If a live connector is unavailable, demonstrate its fixture path explicitly and state the limitation. Do not claim a connected loop is complete without real send/reply/publication evidence. An unanswered PO question stays open while the rest of the workspace remains usable.
